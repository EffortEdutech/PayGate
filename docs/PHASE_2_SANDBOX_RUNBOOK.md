# Phase 2 Sandbox Operations Runbook

This runbook covers local Stripe sandbox operation for the Central Payment Hub.

## Local Ports

The project is locked to the localhost `301#` family. Use `3017` for the Hub unless another Phase 2 service needs it temporarily.

## Required Environment

Use sandbox-only secrets:

```text
PORT=3017
DATABASE_URL=postgresql://payment_hub:change-me@localhost:5432/payment_hub
APP_AUTH_ISSUER=https://payments.example.test
APP_AUTH_AUDIENCE=payment-hub
APP_AUTH_TOKENS=app_analytics_pro:change-me-local-token
STRIPE_SECRET_KEY=sk_test_...
STRIPE_WEBHOOK_SECRET=whsec_...
STRIPE_API_VERSION=2026-02-25.clover
```

Never place live Stripe keys in Phase 2. The adapter rejects `sk_live_` keys.

## Database Setup

Apply migrations in order:

1. `payment-hub/database/migrations/0001_phase1_foundation.sql`
2. `payment-hub/database/migrations/0002_phase2_persistence.sql`
3. `payment-hub/database/migrations/0003_phase2_reconciliation.sql`

## Start Hub

```bash
npm run dev
```

Expected startup URL:

```text
http://127.0.0.1:3017
```

Health check:

```bash
curl http://127.0.0.1:3017/health
```

## Stripe Webhook Forwarding

Point Stripe CLI or dashboard sandbox webhook delivery to:

```text
http://127.0.0.1:3017/v1/webhooks/stripe/primary/test
```

Required header:

```text
Stripe-Signature: generated by Stripe
```

The webhook handler must read raw request bytes. Do not add JSON middleware before signature verification.

## Sandbox Checkout Proof

Call checkout with app credentials and an idempotency key:

```bash
curl -X POST http://127.0.0.1:3017/v1/checkout/sessions \
  -H "Authorization: Bearer change-me-local-token" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: checkout-user-1-growth-monthly-001" \
  -d '{"app_id":"app_analytics_pro","user_ref":"user_1","plan_key":"growth_monthly","return_context":"billing","environment":"test"}'
```

Expected result: a provider-neutral response containing `checkout_session_id`, `redirect_url`, `status`, and `expires_at`.

## Entitlement Verification

After Stripe sends a verified completion or subscription event:

```bash
curl "http://127.0.0.1:3017/v1/entitlements?app_id=app_analytics_pro&user_ref=user_1&environment=test" \
  -H "Authorization: Bearer change-me-local-token"
```

Entitlements must only change after a verified webhook or explicit reconciliation result. Browser redirects never grant access.

## Portal Session Proof

```bash
curl -X POST http://127.0.0.1:3017/v1/billing/portal-sessions \
  -H "Authorization: Bearer change-me-local-token" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: portal-user-1-001" \
  -d '{"app_id":"app_analytics_pro","user_ref":"user_1","return_context":"billing","environment":"test"}'
```

Portal creation requires an existing Hub-owned provider customer mapping.

## Missed Webhook Repair

Run reconciliation after a missed or ambiguous event:

```bash
curl -X POST http://127.0.0.1:3017/internal/reconciliation/run \
  -H "Authorization: Bearer change-me-local-token" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: recon-user-1-001" \
  -d '{"app_id":"app_analytics_pro","user_ref":"user_1","environment":"test"}'
```

Expected statuses:

- `repaired`: Hub projection changed using provider evidence.
- `in_sync`: provider and Hub projections already matched.
- `no_provider_customer`: Hub has no mapped provider customer.
- `no_provider_subscription`: Stripe has no subscription for the mapped customer.
- `failed`: reconciliation failed and should be investigated or retried.

## Webhook Replay

If a webhook was missed, replay from Stripe sandbox tools. The Hub webhook inbox is unique by provider, provider account, environment, and provider event ID, so duplicate deliveries should be accepted without duplicate projection.

## Sandbox Reset

Before resetting Stripe sandbox objects, preserve or clear related local database rows deliberately. Test and live environments must never share credentials, mappings, webhook events, or idempotency scope.

## Secret Safety

Do not log:

- Stripe secret keys;
- webhook signing secrets;
- bearer tokens;
- card data;
- full provider payloads beyond approved audit/evidence retention.
